📚 Descripción del TP

Uso práctico del cluster III-LIDI (IP: 163.10.34.49) utilizando el gestor de carga de trabajo SLURM. Se enfoca en transferencia de archivos SSH/SCP, envío de trabajos, gestión de nodos e inspección de recursos.

📊 Punto 3: Recursos del Cluster

3.1) Comando: sinfo con formato personalizado

$ sinfo -o '%9P %5D %7X %5Y %4c %7Z %10N %11e'

Salida obtenida:

PARTITION NODES SOCKETS CORES CPUS THREADS NODELIST FREE_MEM
Blade* 16 2 4 8 1 nodo[1-16] 1989-6013
XeonPHI 1 1 64 64 1 XeonPHI N/A
GPUS 2 1 1 1 1 GPU[1-2] N/A
📌 Observaciones:
  • Blade*: Es la partición por defecto (indicada por el *), cuenta con 16 nodos, cada uno con 2 sockets, 4 cores por socket, 8 CPUs totales y 1 thread por core. La memoria libre varía entre 1989 MB y 6013 MB.
  • XeonPHI: Partición con un solo nodo especializado, con 64 cores y 64 CPUs.
  • GPUS: Partición con 2 nodos con GPU, configuración mínima de 1 core y 1 CPU.

3.2) Comando: Estado de los nodos

$ sinfo -o '%9P %10N %t'
Nodo Estado Significado
nodo[1-16] idle ✅ Disponibles y listos para ejecutar trabajos
XeonPHI down* ❌ Fuera de servicio (el * indica que el estado fue establecido por un administrador)
GPU[1-2] down* ❌ Fuera de servicio (marcado por administrador)
📌 Conclusión: Solo los 16 nodos de la partición Blade están operativos y disponibles para ejecutar trabajos.

🚀 Punto 4: Lanzar Trabajos a Ejecución

4.d) Explicación del script launch_serie

#!/bin/bash
#SBATCH -N 1                    # 📦 Indica que se requiere 1 nodo para el trabajo
#SBATCH --exclusive             # 🔒 El nodo será de uso exclusivo
#SBATCH --partition=Blade       # 🎯 Especifica partición "Blade"
#SBATCH -o salida.txt           # 📄 Redirige salida estándar
#SBATCH -e errores.txt          # ⚠️ Redirige mensajes de error

echo Iniciando el programa
./serie
echo Fin del programa

4.e) Resultados de la ejecución

📍 Nodo y Core utilizados:
  • Nodo: nodo1
  • Core: 7

Código serie.c:

#define _GNU_SOURCE
#include <stdio.h>
#include <unistd.h>
#include <sched.h>

int main( int argc, char *argv[]) {
   char hostname[128];
   gethostname(hostname, sizeof(hostname));
   printf("Ejecutando en nodo %s, core %d\n", hostname, sched_getcpu());
   return 0;
}
🎯 Propósito: Identificar exactamente en qué recurso físico del cluster se ejecutó el trabajo.
  • gethostname() 🏷️ → Obtiene el nombre del host (nodo)
  • sched_getcpu() 🔢 → Obtiene el número de core asignado por el planificador

4.f) Ejecución en nodo específico diferente

Se seleccionó nodo16 agregando la directiva:

#SBATCH --nodelist=nodo16
✅ Resultado: El trabajo se ejecutó en nodo16, core 2

4.g) Opciones fuera del script

$ sbatch --nodelist=nodo13 launch_serie
✅ Resultado: El trabajo se ejecutó en nodo13, core 2

4.h) Prioridad de opciones: ¿Script vs. Línea de comandos?

Experimento: Script con --nodelist=nodo16 interno, lanzado con sbatch --nodelist=nodo10

🏆 Conclusión: La opción especificada desde la línea de comandos tiene prioridad sobre la especificada dentro del script. El trabajo se ejecutó en nodo10.

📌 Nota sobre NUMA: Aunque en este caso todos los cores (0-7) pertenecen al mismo nodo NUMA 0, la arquitectura del sistema está configurada para soportar acceso no uniforme a memoria, lo cual es característico de sistemas multiprocesador con múltiples sockets.
📌 Observación sobre Swap: Esto es común en entornos de cluster donde los trabajos se ejecutan con recursos asignados exclusivamente y no se requiere swap, ya que SLURM gestiona la asignación de memoria de forma controlada.
